# 提交到 DSH 插件市场 · 操作步骤（全网页版）

> 全程只用浏览器：GitHub 网页 + npm 网站。**不需要命令行**（唯一一处例外见第 8 步，那里必须在本机装一次验证）。
>
> 事实依据：市场应用 `dshmarket` 的 README §"Submit your plugin"；
> 目录仓库 [awesome-dsh-plugin](https://github.com/awesome-dsh-plugin/awesome-dsh-plugin) 的 `contributing.md`（17.6k 星）；
> 以及实测拉取的 `https://awesome-dsh-plugin.com/plugins.json`（4412 条条目）。

---

## 为什么 npm 那步要靠 GitHub Actions

**npm 没有网页发布界面**——官方社区"请求网页发布界面"的讨论至今开着，发布包只有命令行 `npm publish` 一条路。
所以纯网页的做法是：**让 GitHub Actions 在云端替你执行 `npm publish`**，你只在网页上点「Publish release」。

仓库里已经放好了工作流：[.github/workflows/publish.yml](../.github/workflows/publish.yml)。

| 步 | 在哪做 | 做什么 |
| --- | --- | --- |
| 1 | GitHub 网页 | 建仓库、上传文件、加 `dsh-plugin` topic |
| 2 | npm 网站 | 拿一个 Access Token（**不发布**） |
| 3 | GitHub 网页 | 存成 Secret `NPM_TOKEN` |
| 4 | GitHub 网页 | **试运行**工作流（不需要 Token，不发布） |
| 5 | GitHub 网页 | 发 Release → 自动发布到 npm |
| 6 | GitHub 网页 | Fork 目录仓库 → 新建一个 YAML → 提 PR |
| 7 | GitHub 网页 | 等 CI 与人工评审 |
| 8 | **本机** | 装一次验证（要在你机器上装插件、重启 DSH） |

## 第 1 步 · 网页建仓库并放文件

1. GitHub 右上角 **+ → New repository**
   - Repository name：`dsh-nutstore-backup`
   - 选 **Public**（市场只收公开仓库）
   - **不要**勾 "Add a README file" / .gitignore / license（本地已有，勾了会冲突）
   - 点 **Create repository**
2. 新仓库首页点 **uploading an existing file**
3. 把这些拖进去，**保持目录结构**：
   - 根文件：`package.json`、`cordis.patch.yml`、`README.md`、`LICENSE`、`.gitignore`
   - `lib/` 整个目录（11 个文件）
   - 建议也传：`test/`、`docs/`、`.github/`（评审会看代码与测试，这是加分项）
   - **不要传** `node_modules/`（本来也没有）
4. 底部 Commit message 填 `dsh-nutstore-backup: 坚果云备份插件`，点 **Commit changes**
5. 仓库首页右侧 **About → ⚙️（齿轮）** → **Topics** 加 `dsh-plugin` → 保存

> 网页上传对深层目录不友好时，可以用 **Add file → Create new file**：
> 文件名输入 `lib/index.mjs`（输入 `/` 会自动建目录），把内容粘进去，逐个文件重复即可。

> ⚠️ **仓库要满 1 天**才能提收录 PR（CI 自动检查，只过滤"提 PR 前几分钟才建的仓库"）。
> 差一点就明天再提，重新提交没有任何负面影响。

> ℹ️ 建完仓库进 **Actions** 时可能看到"Get started with GitHub Actions"的模板推荐页
> （里面有个 "Publish Node.js Package"）。**那是引导页，直接点 "Skip this and set up a workflow yourself"
> 或离开即可，千万不要点任何 Configure**——我们的工作流已经在仓库里了，
> 再生成一个会导致同一次 Release 上两个工作流同时发布，第二个必然报"版本已存在"。

## 第 2 步 · 在 npm 网站拿一个 Token（不发布任何东西）

1. 打开 https://www.npmjs.com/signup 注册（或用 GitHub 账号登录）
2. 完成邮箱验证后：右上角头像 → **Access Tokens**
3. **Generate New Token → Granular Access Token**
   - Name：`dsh-nutstore-backup-ci`
   - Expiration：按习惯（例如 90 天）
   - Permissions：**Read and write**
   - Packages：**All packages**（首次发布时包还不存在，选具体包会选不到）
4. 生成后**立刻复制**（只显示一次）

顺手确认包名可用：打开 https://www.npmjs.com/package/dsh-nutstore-backup ，显示 404 就是可用
（已用 npm 接口查过，是空的）。

---

## 第 3 步 · 在 GitHub 网页上存这个 Token

1. 你的仓库 → **Settings** → 左栏 **Secrets and variables** → **Actions**
2. **New repository secret**
3. Name 填 `NPM_TOKEN`（必须一模一样，工作流里就这个名字）
4. Secret 粘贴第 2 步复制的 token → **Add secret**

---

## 第 4 步 · 先"试运行"一次（不用 Token，也不发布）

**建议一定做**：本机测试全绿 ≠ GitHub 机器上全绿（系统、路径、依赖都不同）。

1. 仓库 → **Actions** → 左栏点 **Publish to npm**
2. 右上 **Run workflow** → 分支选 `main` → 点绿色 **Run workflow**
3. 等 1~2 分钟，点开这次运行逐步查看

手动触发**不会发布到 npm**（只有 Release 触发才发布），所以现在不需要 Token。它会执行：

安装开发依赖 → 发布前自检 → **9 个测试套件** → `npm pack --dry-run` 核对打包内容 → 打印试运行摘要

- ✅ 全绿 → 继续第 5 步
- ❌ 有红 → 把红色步骤名与日志最后 20 行发我，我来修

---

## 第 5 步 · 发 Release 即自动发布到 npm

1. 仓库 → 右栏 **Releases** → **Draft a new release**
2. **Choose a tag** → 输入 `v0.1.0` → 点 **Create new tag on publish**
3. Release title 随便填（如 `0.1.0`），描述可写这次改动
4. 点 **Publish release**

然后到 **Actions** 看 `Publish to npm` 依次执行：

1. 校验 tag 与 `package.json` 的 `version` 一致（不一致**直接失败**，避免"发了 Release 却没发布成功"）；
2. 发布前自检 `package-check`；
3. 9 个测试套件；
4. `npm publish --access public`；
5. **从 npm 真实回装一次**，核对发出去的包里文件齐全、`cordis.patch.yml` 与两半入口都在
   —— 这是"我自己装过一次"的自动化版本，也是审稿人最认的证据。

全绿后，包出现在 https://www.npmjs.com/package/dsh-nutstore-backup 。

> 以后发新版：网页上改 `package.json` 的 `version`（点开文件 → 铅笔 → Commit），再发对应 tag 的 Release。
>
> ⚠️ 常见卡点：`npm publish` 处报 `401 Unauthorized` / `ENEEDAUTH` → 第 2、3 步的 Token 没配好
> （或已过期、或权限不是 Read and write）。

## 第 6 步 · 提收录 PR（这一步就是"进市场"）

1. 打开 https://github.com/awesome-dsh-plugin/awesome-dsh-plugin → 右上 **Fork** → **Create fork**
2. 在你的 fork 里：**Add file → Create new file**
3. 文件名填（两个下划线，owner 换成你的 GitHub 用户名）：
   ```
   data/plugins/<你的用户名>__dsh-nutstore-backup.yml
   ```
4. 内容（只需改用户名）：

```yaml
url: https://github.com/<你的用户名>/dsh-nutstore-backup
name: <你的用户名>/dsh-nutstore-backup
category: session
description:
  en: 'Backs up DeepSeek Harness sessions, plugin config and workspace memory to Nutstore (Jianguoyun) over WebDAV, with incremental upload, connection test and one-click restore on a new machine.'
  zh: '把 DeepSeek Harness 的会话记录、插件配置与工作区记忆通过 WebDAV 增量备份到坚果云，支持连接测试与在新机器上一键恢复。'
```

5. 拉到底 **Commit changes**（可直接提交到 main）
6. 回 fork 首页点 **Contribute → Open pull request** → 填标题 `Add dsh-nutstore-backup` → **Create pull request**

**格式要点**（都写在他们的 `contributing.md` 里）：

- `description.en` **必须以句号结尾**；
- 描述含 `: `（冒号+空格）**必须加引号**——上面 `en` 用单引号包住就是为这条，否则 YAML 解析失败；
- **描述必须属实**，审稿人逐条对代码。这句只说"增量上传 / 连接测试 / 一键恢复"，与实现一致，没有夸大；
- `category` 选贴合的：`session`（核心是会话与迁移）或 `dev` 都合理；选不准维护者会直接改，不因此打回；
- 只加**这一个文件**，不要动两个 README（由脚本生成，手工改会冲突）。

---

## 第 7 步 · 等 CI 与人工评审

- CI 校验形式：manifest、仓库年龄、YAML 格式、README 能否重新生成。**通过是前提，不是结论**；
- 维护者会真读仓库，核对描述是否名副其实；
- 合并后 CI 重新生成两个 README，站点与市场**通常一天内**出现你的条目。

---

## 第 8 步 · 装一次验证（必须在本机）

没有网页等价物：要在你机器上装插件、重启 DSH 看设置页。

```powershell
dsh plugin --profile web add dsh-nutstore-backup
```

若没有 `dsh` 命令（桌面版），用手工方式，见 README §2.2。装完**重启 DSH** →
打开 **设置 → 坚果云备份**，确认页面出现、能登录、能备份。

这一步的结果值得写进 PR 描述（"已用 `dsh plugin add` 装过并跑通备份/恢复预览"）——审稿人最认这种证据。

## 附 B · 背景资料

### 市场链路

```
你的 GitHub 仓库  ──收录 PR──▶  awesome-dsh-plugin/data/plugins/<owner>__<repo>.yml
                                      │ CI 每天生成
                                      ▼
                          awesome-dsh-plugin.com/plugins.json
                                      │ 市场每次打开时实时拉取
                                      ▼
                     DSH 里的「插件市场」列表 → 用户点一下安装
                                      │
                                      ▼
                        dsh plugin --profile web add <你的包名>   （从 npm 取）
```

**两件事都要做**：发布到 **npm**（用户安装时从这里取包）＋ 往 **awesome-dsh-plugin** 提 PR（进市场列表）。
只发 npm 不会出现在市场；只提 PR 而 npm 上没有包，用户点安装会失败。

### 常见被打回的原因（对照自查）

| 原因 | 本项目 |
| --- | --- |
| 只声明 `dsh.client`、没有 `dsh.bundle` → 装不上 | ✅ 有 `dsh.bundle.patch` + `cordis.patch.yml` |
| 占位/纯 README 仓库 | ✅ 完整实现 + 9 个测试套件 |
| 仓库未满 1 天 | ⏳ 建完等一天 |
| 没加 `dsh-plugin` topic | ⏳ 推完记得加 |
| 描述夸大（写了数字/API 但代码里没有） | ✅ 描述只写实际能力 |
| 描述含 `: ` 未加引号 | ✅ 已用单引号 |
| 打包把测试发出去 | ✅ `files` 只含 lib/、cordis.patch.yml、README.md |

### 发布前最后的自检

```powershell
cd "D:\My Agent\dev\dsh-nutstore-backup"
node test/run-all.mjs        # 9 个套件应全绿（约 7 秒）
node test/package-check.mjs  # 发布前自检必须 ✅
```

- [ ] `package-check` 通过
- [ ] `private` 为 false（当前已满足）
- [ ] `npmjs.com/package/dsh-nutstore-backup` 显示 404（名字可用）
- [ ] 打包只含 lib/、cordis.patch.yml、README.md（不含 test/、node_modules）
- [ ] GitHub 仓库已创建、已加 `dsh-plugin` topic、创建满 1 天
- [ ] Actions 里试运行过一次且全绿
- [ ] `dsh plugin add` 装完重启能看到设置页
- [ ] `data/plugins/<owner>__dsh-nutstore-backup.yml` 已按格式提 PR

### 建议补的仓库内容

评审与用户都更愿意装"看得见界面"的插件。建议发 PR 前在 README 里补两张图：
设置页（登录 + 恢复分区）与一次备份的结果 JSON。图片放仓库里用相对路径引用即可。
